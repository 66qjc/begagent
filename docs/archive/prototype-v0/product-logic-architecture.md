# 大学生求职执行 Agent：产品逻辑架构

> 文档状态：产品框架基线（需求讨论阶段）  
> 当前版本：v0.2  
> 更新日期：2026-08-24  
> 说明：本文记录当前已经讨论并认可的产品逻辑。标记为“待确认”或“暂缓”的部分，不视为最终需求，也不作为当前开发承诺。

## 1. 文档目的

本文用于统一产品定位、核心对象、三类业务 Agent、职业领域包、协作机制、分层记忆、权限边界以及第一轮比赛演示闭环。

当前阶段只确定产品逻辑架构，不开始制作 MVP，不确定最终页面形态，也不提前固化尚未讨论完的算法、字段和技术选型。

### 1.1 决策状态

| 状态 | 含义 |
|---|---|
| 已确定 | 已形成一致意见，可以作为后续设计基线 |
| 框架确定，细节待确认 | 大方向保留，内部规则、字段或算法后续讨论 |

| 最后讨论 | 等业务逻辑、记忆与比赛闭环稳定后再决定 |

## 2. 产品定位

### 2.1 一句话定义

> 面向大学生的 AI 求职代理系统：从用户真实经历出发，最大化展示其优势，帮助用户发现并判断岗位、准备和执行申请、持续与 HR 沟通；当用户与目标岗位存在差距但仍希望尝试时，系统进一步把差距转化为成长任务和新证据，再更新求职材料并进入下一轮求职行动。

产品最终追求的不是“生成一份简历”，而是：

> 在不虚构核心事实的前提下，持续提高用户获得目标工作的概率。

### 2.2 核心闭环

```text
用户真实经历与职业目标
          ↓
       包装自己
       PREPARE
          ↓
       执行求职
        APPLY
          ↓
       获得反馈
          ↓
       补强自己
        GROW
          ↓
更新经历证据、简历和求职策略
          ↓
     再次申请 / 获得 Offer
```

### 2.3 产品不是什么

- 不是单纯的 AI 简历生成器。
- 不是只给出“岗位匹配度百分比”的推荐工具。
- 不是无差别批量海投机器人。
- 不是三个彼此独立的聊天机器人。
- 不是用 MBTI 直接决定用户职业的测评产品。
- 不代替用户参加正式笔试、测评或面试。

## 3. 目标用户与职业覆盖

### 3.1 第一核心用户

- 大三、准备实习或暑期实习的学生。
- 大四及临近毕业、准备校招的学生。
- 想跨专业或转向新职业方向的学生。
- 已有零散经历，但不会提炼和表达优势的学生。
- 与目标岗位存在差距，但愿意通过学习和项目进行挑战的学生。

### 3.2 不按专业限制用户

产品不采用“某个专业只能投某类岗位”的静态映射，而采用：

```text
专业与课程
    ↓
可迁移能力
    ↓
技能与经历证据
    ↓
岗位族
    ↓
具体岗位 JD
```

同一专业可以进入多个岗位族；同一个岗位族也可以接受来自不同专业、但拥有可迁移能力的用户。

## 4. 产品顶层逻辑架构

```text
                           大学生用户
                               │
                    职业方向探索（可跳过）
                               │
                           求职计划
                 Career Mission / 顶层业务容器
                               │
              ┌────────────────┼────────────────┐
              │                │                │
          当前阶段         任务编排与交接      权限与用户接管
              │                │                │
              └────────────────┼────────────────┘
                               │
          ┌────────────────────┼────────────────────┐
          ↓                    ↓                    ↓
    优势简历 Agent       求职执行 Agent       面试成长 Agent
       PREPARE               APPLY                GROW
          │                    │                    │
          └────────────────────┼────────────────────┘
                               │
                    职业领域包 Domain Pack
                               │
                    分层职业记忆系统 Memory
                               │
        岗位源 / 简历工具 / 申请渠道 / HR 会话 / 学习与测评工具
```

其中：

- 三个 Agent 负责不同业务目标。
- 任务编排层负责状态、任务交接与权限，不是第四个 Agent。
- 职业领域包提供不同岗位所需的知识与判断标准。
- 记忆系统负责保存事实、上下文和产物，不负责替用户决策。

## 5. 顶层业务对象：求职计划

一个用户可以拥有多个求职计划。每个计划对应一个相对一致的职业方向和求职周期。

```text
一个用户
│
├─ 全局个人档案
│  ├─ 基础信息
│  ├─ 经历与技能
│  ├─ 兴趣与职业偏好
│  └─ 长期职业记忆
│
├─ 求职计划 A：AI 产品实习
├─ 求职计划 B：数据分析校招
└─ 求职计划 C：新能源产品岗位
```

### 5.1 每个求职计划包含

- 求职类型：日常实习、暑期实习、秋招或春招。
- 一个主要岗位族和最多两个相邻岗位方向。
- 城市、行业、到岗时间、实习时长、薪资等现实条件。
- 用户不接受的条件和沟通边界。
- 当前加载的职业领域包。
- 用户选择启用的业务 Agent。
- 当前阶段、任务负责人、已完成任务和下一步行动。
- 独立的岗位、投递、HR 对话、面试及反馈记录。

跨度过大的岗位应拆分为不同求职计划，避免不同简历策略和求职反馈互相污染。

## 6. 三个可选择启用的业务 Agent

### 6.1 优势简历 Agent

目标：在不虚构核心事实的前提下，帮助用户发现、组织并最大化表达真实优势。

核心职责：

- 导入和整理已有简历、项目、比赛、实习、课程和校园经历。
- 通过自适应访谈追问用户真正做过什么。
- 将口语化经历转化为企业能够理解的职业价值。
- 建立可复用的职业素材与证据。
- 针对不同岗位重组经历顺序、重点和表达方式。
- 生成岗位定制的正式简历。
- 对待确认信息、合理提炼和无依据内容进行区分。

当前范围只把“正式简历”作为主要申请材料。自我介绍、求职信、作品说明、HR 开场白和项目补充材料暂不纳入当前范围。

### 6.2 求职执行 Agent

目标：帮助用户把求职目标转化为真实、持续、可管理的求职行动。

核心职责：

- 导入、发现和整理岗位。
- 解析 JD 与硬性条件。
- 判断能否申请、用户是否喜欢、竞争证据强弱及投入价值。
- 生成有理由、有风险提示的投递建议。
- 管理岗位机会池与投递队列。
- 在用户授权范围内辅助填写申请。
- 与 HR 进行有上下文的多轮沟通。
- 在敏感问题和承诺性动作前请求用户确认。
- 维护申请状态并将真实结果反馈给其他 Agent。

### 6.3 面试成长 Agent

目标：识别用户为了目标岗位还需要补齐什么，并通过训练、模拟和真实成果帮助用户成长。

在总体闭环中的职责已经确定：

- 投递前：识别差距、设计短期补强和岗位证据冲刺。
- 投递中：帮助用户理解目标岗位和可迁移能力。
- 面试前：以面试官身份进行自适应、多轮、带追问的模拟面试。
- 面试后：根据真实反馈区分知识、技能、经历和表达问题。
- 成长完成后：将新成果写回职业素材库，并触发简历和求职策略更新。

其内部测评方法、问题生成、评分标准和学习路径细节暂缓设计。

## 7. 职业方向探索

职业方向探索是三个业务 Agent 之前的可选入口，不是第四个业务 Agent。

```text
专业与课程经历
+ 已有技能与熟练程度
+ 项目、比赛和实习
+ 兴趣爱好
+ 工作内容与环境偏好
+ MBTI 等性格参考
            ↓
        职业方向探索
            ↓
推荐可能感兴趣的岗位族及原因
            ↓
      用户自主选择目标岗位
            ↓
        创建求职计划
```

判断权重原则：

- 高权重：真实技能、能力证据、项目经历和现实限制。
- 中权重：兴趣爱好、工作环境偏好和长期目标。
- 低权重：MBTI、性格测试和职业测评结果。

MBTI 只能辅助解释偏好，不得成为排除用户进入某个岗位的依据。

## 8. 职业领域包

职业差异通过可插拔的职业领域包实现，不为每个专业重新创建一个 Agent。

### 8.1 第一批“4+4”职业领域

| 类别 | 职业领域包 | 代表岗位 |
|---|---|---|
| 数字技术 | AI 应用与 AI 产品 | AI 产品、Agent 应用、AI 解决方案、AI 运营 |
| 数字技术 | 软件与应用开发 | 前端、后端、客户端、软件测试、实施工程师 |
| 数字技术 | 数据分析与数据产品 | 数据分析、商业分析、BI、数据产品助理 |
| 数字技术 | 数字运营与电商 | 用户运营、产品运营、电商运营、跨境电商、内容运营 |
| 其他热门方向 | 智能制造与新能源 | 机械、电气、自动化、工艺、设备、质量工程师 |
| 其他热门方向 | 财务金融与审计 | 会计、财务分析、审计、银行运营、风控 |
| 其他热门方向 | 供应链与物流 | 采购、供应链计划、物流运营、生产计划 |
| 其他热门方向 | 市场与商务 | 市场营销、品牌、公关、销售、商务拓展 |

### 8.2 每个领域包包含

```text
职业领域包
│
├─ 岗位地图与岗位别名
├─ 校招和实习常见要求
├─ 简历经历价值与表达规则
├─ 硬性条件和投递决策规则
├─ HR 沟通中的行业问题
├─ 面试能力模型和评价标准
├─ 技能差距与成长任务模板
└─ 行业特有风险与现实限制
```

完整产品支持多个职业领域；第一轮比赛演示只选择一个领域完成黄金闭环，不同时实现八个领域的全部细节。

## 9. 优势挖掘与职业素材库

### 9.1 自适应优势访谈

```text
用户自然讲述经历
        ↓
识别有价值但不完整的信息
        ↓
只追问当前最关键的问题
        ↓
拆解事实、行动、工具、结果和能力
        ↓
信息足够后停止追问
```

每段经历形成一个职业素材单元：

```text
经历名称
├─ 背景与目标
├─ 用户真实角色
├─ 实际完成的行动
├─ 使用的工具与技能
├─ 解决的问题
├─ 产生的结果
├─ 可以证明的能力
├─ 可用于哪些岗位
├─ 证明材料
└─ 仍需用户确认的信息
```

### 9.2 简历美化边界

允许：

- 选择和突出对岗位最有价值的真实事实。
- 将校园语言翻译为企业可以理解的职业语言。
- 改变经历顺序、篇幅和强调重点。
- 根据岗位重构同一经历的叙事角度。
- 在用户确认后使用可靠数字。

禁止：

- 将参与自动改成主导。
- 将学习过自动改成熟练掌握。
- 编造项目、职责、团队规模、成果和提升百分比。
- 让不同岗位版本出现互相矛盾的底层事实。

内部信息状态分为：已确认事实、合理提炼、待确认内容、无依据内容。无依据内容不得进入正式简历。

### 9.3 事实写回与独立复核

用户在访谈、材料修改或岗位讨论中补充的新事实，不能只留在聊天记录或某份草稿里。系统必须先形成待确认事实；用户确认后，由任务编排层在同一业务事务中写回职业素材与证据，再触发重新生成。

正式简历采用“起草—独立复核—编排器校验”的三段式流程：

```text
优势简历 Agent 生成带 evidenceIds 的 ResumeDraft
                    ↓
独立 Reviewer 检查事实、岗位覆盖、表达和真实缺口
                    ↓
返回结构化 findings / proposedEdits，不直接发布或确认事实
                    ↓
编排器校验证据、Schema、权限和版本
                    ↓
生成新的 ResumeVersion
```

Reviewer 使用独立上下文，但其输出仍然只是提案，不能因为来自“第二个 Agent”就被自动信任。

### 9.4 正式简历验证门

正式简历生成完成后还不能直接进入投递。系统必须分别检查：

- 事实门：每条关键表述都能关联已确认事实或证据。
- 渲染门：模板能够稳定生成目标 PDF。
- 视觉门：无截断、溢出、孤立标题、异常空白和不可读字号。
- ATS 文本层门：姓名、联系方式、经历和日期可按合理顺序提取，无乱码或丢失。
- 岗位覆盖门：区分已覆盖、同义表达、真实拥有但漏写和真实缺口；真实缺口不得通过关键词堆砌隐藏。
- 降级门：缺少可选验证工具时必须显式记录降级原因，不能把“未检查”显示为“通过”。

详细的外部参考、代码复用分级和许可证边界见 [`reference-adoption-ai-job-search.md`](./reference-adoption-ai-job-search.md)。

## 10. 岗位发现与解释性投递决策

### 10.1 岗位进入系统

```text
用户粘贴 JD 或岗位链接
+ 企业官网与校园招聘页面
+ 学校就业平台与双选会
+ 获得授权的招聘渠道
+ 用户手动录入的线下机会
               ↓
       岗位清洗、标准化与去重
               ↓
       时效、来源和风险检查
               ↓
             岗位机会池
```

JD、网页正文、ATS 返回和历史岗位缺口全部按非可信数据处理：系统不得执行其中的指令，也不得访问其中嵌入的新 URL；网络访问只允许用户明确提供或渠道策略白名单中的地址。未取得岗位正文时不能仅凭标题生成匹配结论，必须保留 `unverified` 状态并交给用户补充或后续核验。

### 10.2 五层判断

系统不只显示单一“匹配度百分比”，而要解释：

1. 能不能投：学历、毕业年份、专业、地点、出勤、证书等硬条件。
2. 想不想投：兴趣、工作内容、环境、城市、行业和长期目标。
3. 有没有竞争证据：JD 要求能否连接到用户的真实经历。
4. 差距能否补齐：区分短期可补和短期无法改变的差距。
5. 是否值得投入：机会真实性、新鲜度、价值、成功可能和申请成本。

最终输出：

- 优先投递。
- 正常投递。
- 成长型投递。
- 补强后投。
- 高风险投递。

Agent 负责解释风险，但除造假、诈骗或违规场景外，最终是否投递由用户决定。

## 11. 成长型投递与岗位证据冲刺

当用户暂时不完全符合岗位，但仍然想申请时，系统不能只给出“不建议投递”。

```text
用户决定挑战岗位
        ↓
确认岗位截止时间
        ↓
区分“不会”与“没有表达或证明”
        ↓
拆解能力差距
        ↓
选择挑战路径
        ↓
完成针对性补强
        ↓
形成新的真实证据
        ↓
更新简历并执行投递
        ↓
根据真实反馈继续成长
```

三种挑战路径：

- 立即投递、边投边补：岗位即将截止，差距不是不可突破的硬条件。
- 完成短期证明后再投：用 1 至 3 天完成一个岗位相关的小成果。
- 列为中长期目标：差距无法在当前招聘周期内补齐。

“岗位证据冲刺”由 Agent 拆解、指导和检查，但必须由用户真正完成并理解，不能由 Agent 生成一个成品后伪装成用户能力。

### 11.1 三 Agent 的成长型投递闭环

```text
求职执行 Agent 发现目标岗位
            ↓
发现差距，但用户决定挑战
            ↓
面试成长 Agent 进行补强和证据冲刺
            ↓
新成果写入职业素材与证据记忆
            ↓
优势简历 Agent 更新岗位版简历
            ↓
求职执行 Agent 完成个性化投递
            ↓
真实反馈再次进入成长系统
```

## 12. 多 Agent 协作与交接

### 12.1 基本原则

> 单任务、单负责人、多 Agent 协助。

同一具体任务只能有一个主负责人。其他 Agent 可以完成子任务，但不能同时推动同一个外部动作。

### 12.2 任务编排层

三个 Agent 之上使用确定性的任务编排层，而不是管理 Agent。

任务编排层负责：

- 保存求职计划和当前任务状态。
- 标识当前任务负责人。
- 创建、分发和恢复协作任务。
- 检查用户授权和动作风险。
- 防止重复或冲突执行。
- 保存操作与交接记录。

### 12.3 两种跨 Agent 方式

协助调用：主负责人不变，另一个 Agent 完成子任务后返回结果。

```text
求职执行 Agent
    ↓ 请求定制简历
优势简历 Agent
    ↓ 返回简历版本
求职执行 Agent 继续申请
```

阶段交接：任务主要目标变化，负责人正式切换。

```text
求职执行 Agent 收到面试邀请
        ↓
整理岗位、申请和 HR 上下文
        ↓
交接给面试成长 Agent
        ↓
完成准备与模拟
        ↓
真实面试结束后交回求职执行 Agent
```

### 12.4 结构化交接协议

Agent 之间不依赖无边界自由聊天，而使用结构化任务包：

```text
Agent 任务包
├─ 所属求职计划
├─ 目标岗位与岗位案例
├─ 当前目标和主负责人
├─ 用户已确认事实的记忆引用
├─ 允许使用的材料
├─ 已发现的问题
├─ 请求对方完成的子任务
├─ 权限范围
├─ 截止时间
└─ 预期返回的结构化产物
```

跨 Agent 的完整过程是：

```text
任务交接
   ↓
按任务范围装载相关记忆
   ↓
新 Agent 完成任务
   ↓
结果写回对应记忆层
   ↓
触发原 Agent 或下一个 Agent 继续工作
```

## 13. 分层职业记忆系统

记忆系统是三个 Agent 的共享职业上下文和跨阶段协作底座，不是第四个 Agent。

```text
                    求职计划
                       │
                 任务编排层
                       │
              分层职业记忆系统
       ┌───────────────┼───────────────┐
       ↓               ↓               ↓
优势简历 Agent    求职执行 Agent    面试成长 Agent
```

### 13.1 六层记忆

| 记忆层 | 主要内容 | 主要维护者 |
|---|---|---|
| 用户长期记忆 | 教育、技能、兴趣、长期偏好、沟通边界 | 用户为主，优势简历 Agent 辅助 |
| 职业素材与证据 | 经历事实、能力证据、作品、简历版本 | 优势简历 Agent、面试成长 Agent |
| 求职计划记忆 | 目标、限制、授权、策略、当前阶段 | 任务编排层 |
| 岗位案例记忆 | JD、匹配分析、投递、HR 对话、面试与状态 | 求职执行 Agent |
| 临时工作记忆 | 当前草稿、推断、待确认问题和中间计划 | 当前任务负责人 |
| 操作与交接记录 | 读取、修改、授权、交接和外部动作 | 系统自动追加 |

### 13.2 记忆状态与来源

重要记忆不仅保存文本，还要保存：

- 内容及结构化类型。
- 信息来源。
- 是否经过用户确认。
- 证据或关联产物。
- 适用岗位或求职计划。
- 创建者、更新时间和版本。
- 敏感级别和可读取范围。
- 是否过期、归档或删除。

### 13.3 作用域与最小读取

- 优势简历 Agent 默认读取经历、技能、岗位要求和简历反馈。
- 求职执行 Agent 默认读取求职条件、岗位档案、获批简历和 HR 上下文。
- 面试成长 Agent 默认读取 JD、能力证据、面试反馈和学习记录。
- 未确认推断不得被求职执行 Agent 当成事实提交。
- Agent 不读取与当前任务无关的敏感信息或完整历史对话。

HR 长对话保存原始消息、当前摘要、已确认事实、待回答问题、招聘进度和下一步上下文，使用户接管后仍可交回 Agent 继续。

记忆具体字段、检索、压缩、冲突解决和删除机制属于后续细节，当前只确定分层与作用域原则。

## 14. 用户授权与执行边界

### 14.1 四级动作权限

| 等级 | 默认策略 | 示例 |
|---|---|---|
| 绿色 | 可自动执行 | 搜索、解析、排序、生成草稿、更新内部状态 |
| 黄色 | 获得范围授权后执行 | 执行已批准投递、低风险 HR 回复、按规则跟进 |
| 红色 | 每次必须确认 | 薪资、到岗、地点、面试安排、敏感信息、Offer 决策 |
| 黑色 | 禁止代替用户执行 | 编造经历、代考、冒充面试、伪造证明、签署合同 |

### 14.2 三种使用模式

- 建议模式：Agent 只分析和生成内容，外部操作由用户完成。
- 协作模式：Agent 执行低风险动作，投递和关键沟通需要确认；作为默认模式。
- 托管模式：Agent 在预授权范围内持续工作，关键节点仍必须交回用户。

授权需要精确到求职计划、岗位类型、平台、动作、时间和暂停条件，用户可随时暂停、撤销授权或接管。

### 14.3 渠道执行策略

```text
官方 API 或书面合作
→ 按授权范围执行

允许辅助的企业官网 / ATS
→ 自动填写 + 用户最终确认

只允许用户操作的渠道
→ Deep Link / 浏览器交接

条款禁止自动化的渠道
→ 不执行自动操作
```

登录、扫码、短信验证码、滑块、人脸验证和最终高风险提交都属于人机交接点，不设计绕过机制。

## 15. HR 多轮沟通

HR 沟通是一项持续存在、具备岗位上下文的任务，不是一次性话术生成。

```text
岗位上下文
+ 本次申请材料
+ 用户已确认信息
+ 历史 HR 对话
+ 用户沟通边界
        ↓
求职执行 Agent
        ↓
自动回复 / 请求确认 / 转交用户接管
```

可自动处理的低风险内容包括礼貌开场、确认收到、索要完整 JD、询问招聘流程和按授权进行礼貌跟进。

涉及薪资、到岗时间、工作地点、实习时长、加班出差、面试安排、经历真实性、敏感信息或表达不明确的问题时，必须暂停并请求用户确认。

### 16.1 演示原则

完整产品覆盖多个职业领域，但第一轮只演示一条足够深、真实运行的黄金路径。建议使用“大学生挑战 AI 产品实习岗位”作为主案例。

      ↓

      ↓

## 17. 产品与代码架构创新

### 17.1 成长型投递闭环

产品不仅寻找当前适合用户的岗位，还把用户主动想挑战的岗位差距转化为成长任务、新证据和下一次求职行动。

### 17.2 结构化多 Agent 协作

创新不在 Agent 数量，而在单任务单负责人、结构化交接协议、可恢复状态和正式产物写回。

### 17.3 分层职业记忆

不同 Agent 不共享无限增长的聊天记录，而是按任务读取带来源、状态、版本和权限的职业记忆。

### 17.4 证据约束的职业表达

简历重要表述可以回溯到用户确认事实或真实成长成果，系统允许强化表达，但不允许无依据扩写。

### 17.5 权限门控与渠道策略

外部动作根据风险、用户授权和渠道规则决定自动执行、请求确认、用户接管或禁止执行。

### 17.6 可观察、可回放的执行过程

任务状态、Agent 交接、记忆读取、产物版本、用户确认和外部动作形成事件轨迹，可用于比赛展示、故障恢复和后续评测。

### 17.7 可验证的正式申请材料

简历交付不是一次文本生成，而是事实引用、独立复核、PDF 渲染、视觉检查和 ATS 文本层检查共同通过的可审计流水线。任一强制门失败时，材料保持草稿状态，不能进入投递审批。

## 18. 当前确定的产品主张

> 本项目面向大学生构建一个以求职目标为中心的多 Agent 执行系统。不同于只生成简历、推荐岗位或模拟面试的单点工具，系统通过结构化任务编排、分层职业记忆与证据约束，让优势简历 Agent、求职执行 Agent 和面试成长 Agent 围绕同一求职计划持续协作。当用户与目标岗位存在差距但仍希望尝试时，系统不会简单拒绝推荐，而是启动成长型投递：将能力差距转化为可完成的证据任务，把真实成长结果写回职业记忆并更新申请材料，最终在人机授权边界内完成申请与跟进。
